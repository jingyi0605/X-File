# 需求文档：子标签互斥与单选管理

状态：完成

## 简介

当前标签树表达层级关系，但同一父标签下的子标签可以同时赋给文件。对“项目状态/方案沟通”“项目状态/项目投标”“项目状态/合同签订”这类状态标签，用户希望启用单选模式：选择其中一个时，另一个不再作为该文件的有效状态标签。本功能须接入现有标签管理、文档/文件夹赋值、智能规则和标签重算流程，且不能改变未启用单选的旧标签行为。

## 术语表

- **父标签**：具有一个或多个直接子标签的标签节点。
- **子标签选择模式**：父标签配置，`multiple` 表示直接子标签可并存，`single` 表示同一文件至多有一个直接子标签有效。
- **来源标签**：由手工文档绑定、文件夹绑定、智能规则或系统派生路径产生的标签。
- **有效标签**：经过来源合并及单选冲突裁决后，供浏览、搜索、标签计数和导出使用的标签集合。
- **System**：X-File 文档库。

## 范围说明

### In Scope

- 在父标签定义中持久化子标签选择模式，并在标签管理 UI 配置。
- 手工给文档或文件夹选中单选组的子标签时，替换当前编辑集合中的兄弟子标签。
- 在统一有效标签解析链路中处理手工、文件夹绑定、智能规则和系统派生标签的冲突。
- 兼容不含新字段的旧数据；启用单选时保留源绑定，不静默批量删除数据。
- 在桌面 Native Core 与仍支持的 HTTP/Node 服务路径实现一致语义。

### Out of Scope

- 任意自定义互斥组、跨父标签互斥或跨层级递归组。
- 改造 `and`、`or`、`not` 智能规则表达式或增加标签间规则语言。
- 禁止父标签与其子标签同时存在；本功能只限制同一父标签下的直接子标签。
- 默认对现有数据做破坏性迁移或删除冲突来源。

## 需求

### 需求 1：父标签选择模式

**用户故事：** 作为标签管理员，我希望为父标签设置子标签可多选或单选，以便把状态类子标签配置为互斥，而不影响普通分类标签。

#### 验收标准

1. WHEN 创建或编辑父标签 THEN System SHALL 显示“允许多选 / 仅允许一个”设置，并保存到父标签定义。
2. WHEN 标签定义不含该字段或该值无效 THEN System SHALL 按 `multiple` 处理，维持既有行为。
3. WHEN 保存选择模式 THEN System SHALL 通过现有标签详情接口返回该配置，且不改变标签 ID、路径和规则契约。
4. WHEN 父标签没有直接子标签 THEN System SHALL 允许先保存模式，后续新增的直接子标签继承该约束。

### 需求 2：手工标签赋值替换

**用户故事：** 作为文档库用户，我希望在单选组中选择新子标签时自动替换旧子标签，以便文件状态保持唯一。

#### 验收标准

1. WHEN 用户在文档或文件夹赋值编辑器中选择某单选组子标签 THEN System SHALL 在提交前从同一选择集合中移除其兄弟子标签。
2. WHEN 赋值请求包含同组多个直接子标签 THEN System SHALL 由权威写入路径拒绝无效输入或以明确、可测试的替换语义归一化，不能依赖无契约的数组顺序。
3. WHEN 标签属于不同父标签或父标签为 `multiple` THEN System SHALL 保留其并存行为。
4. WHEN 用户取消一个子标签 THEN System SHALL 不自动选择其他兄弟标签。

### 需求 3：多来源有效标签互斥

**用户故事：** 作为用户，我希望文件通过不同来源获得标签后仍遵守单选配置，以便重算不会重新出现互斥状态。

#### 验收标准

1. WHEN 同一文件的来源合并产生单选组中多个直接子标签 THEN System SHALL 在统一有效标签解析结果中至多保留一个。
2. WHEN 冲突来自不同来源 THEN System SHALL 按设计中规定的来源优先级和同级裁决规则稳定选择结果。
3. WHEN 启用单选或调整相关标签规则/绑定 THEN System SHALL 触发必要的标签重算/增量导出，使浏览、搜索、计数与导出一致。
4. WHEN 用户移除高优先级来源标签 THEN System SHALL 重新显示仍由低优先级来源提供且符合规则的子标签。

### 需求 4：既有冲突与来源透明度

**用户故事：** 作为标签管理员，我希望启用互斥时了解已有冲突，但不丢失原始绑定，以便安全整理数据。

#### 验收标准

1. WHEN 开启单选且已有冲突来源 THEN System SHALL 仅在有效标签视图中裁决，不自动删除文档绑定、文件夹绑定或智能规则。
2. WHEN 有效结果因单选而隐藏来源标签 THEN System SHALL 能通过标签详情/来源信息或管理提示说明被裁决的标签与来源。
3. WHEN 同级冲突没有明确业务优先级 THEN System SHALL 使用稳定的确定性规则，并可在相同输入下重复得到相同结果。

### 需求 5：兼容与实现一致性

**用户故事：** 作为现有用户，我希望升级后旧标签仍正常工作，并且桌面与服务端模式结果一致。

#### 验收标准

1. WHEN 读取历史标签存储和旧请求 THEN System SHALL 对缺失配置采用多选默认值，不要求一次性数据迁移。
2. WHEN 在桌面原生路径与仍支持的服务端路径处理同一标签数据 THEN System SHALL 产生相同的赋值验证、来源优先级和有效标签结果。
3. WHEN 标签被移动、更名、停用或删除 THEN System SHALL 按现有标签管理语义更新父子关系，不留下失效互斥配置引用。

## 非功能需求

### 非功能需求 1：性能

1. WHEN 解析单个文件标签 THEN System SHALL 仅基于该文件已有来源与相关父子标签完成裁决，不执行全库扫描。
2. WHEN 模式变更影响全库有效标签 THEN System SHALL 复用现有异步标签重算和任务中心机制。

### 非功能需求 2：可靠性

1. WHEN 标签重算或导出失败 THEN System SHALL 保留失败状态与错误，不把未完成结果报告为成功。
2. WHEN 配置或绑定写入失败 THEN System SHALL 不留下半写入的父标签模式或绑定集合。

### 非功能需求 3：可维护性

1. WHEN 多来源标签合并 THEN System SHALL 由单一共享语义的解析/裁决逻辑保障一致性，避免 UI 独自承担互斥规则。
2. WHEN 增加新的标签来源 THEN System SHALL 明确其裁决优先级，并纳入同一解析链路测试。

## 成功定义

- 用户可在父标签管理中启用/关闭子标签单选，旧标签默认行为不变。
- “项目状态”启用单选后，手动赋予任一状态子标签会替换同组旧标签；重算后的有效标签仍至多有一个。
- 文件夹、规则等不同来源的冲突遵循明确、稳定且可解释的优先级。
- 桌面 Native Core 与受支持服务端路径的相关测试结果一致。
