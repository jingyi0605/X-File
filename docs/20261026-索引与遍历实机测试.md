# 索引与遍历实机测试

本报告记录本轮追加优化前的基线。后续实现和复测结果见 [索引优化复测报告](20261026-索引优化复测报告.md)。

测试日期：2026-10-26。原始测量数据见 [实机测试数据](20261026-索引与遍历实机测试数据.json)。

## 测试方式与边界

- 环境：Apple M4，10 个逻辑 CPU，16 GiB 内存，macOS 26.5，ARM64。
- 启动当前 Rust debug 桌面程序和 Vite 前端，由真实桌面窗口执行刷新、目录浏览和搜索；没有启动 Node 后端。
- 使用独立 `X_FILE_DATA_DIR` 和临时文档库，没有使用用户原有资料库。测试结束后关闭测试程序和前端服务，清理生成的测试库。
- 初始文档库包含 10,000 个 Markdown 文件、100 个目录，正文合计 13,598,890 字节。正文较短，不能代表大型 PDF、Office、网络磁盘或生产发布构建的表现。
- 桌面程序通过 `X_FILE_DESKTOP_CLI_PATH` 进入测量包装脚本，再启动当前真实原生 worker。脚本记录输入范围、子进程耗时、CPU 时间、峰值 RSS，以及导出文件的 inode、mtime 和大小变化，没有替换索引实现。
- 表内任务耗时包含真实 worker 进程启动、索引与导出；排除包装脚本前后收集文件属性的时间。界面等待还包含调度、包装脚本、轮询和渲染，不能直接等同于表内耗时。
- `indexTimingsMs.total` 包含状态读取、遍历、元数据比较、摘要提取和索引快照持久化，不是纯 `readdir` 时间。导出阶段的估算为任务总耗时减去该指标，仍包含少量进程和调度开销。
- 没有清空操作系统文件缓存，也没有运行优化前版本；这些数据不能用于宣称相对旧实现提升了多少倍。

## 真实桌面运行结果

| 场景 | worker 耗时 | 索引阶段 | 扫描文件 | 实际重建文档 | 重写导出文件 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 首次完整建库 | 9,707ms | 3,151ms | 10,000 | 10,000 | 10,126 |
| 无变化刷新，第 1 次 | 549ms | 410ms | 10,000 | 0 | 0 |
| 无变化刷新，第 2 次 | 587ms | 453ms | 10,000 | 0 | 0 |
| 监听单文件追加，摘要词项不变 | 811ms | 524ms | 1 | 1 | 4 |
| 监听单文件修改，搜索词项变化 | 2,049ms | 561ms | 1 | 1 | 18 |
| 删除临时新增文档 | 2,051ms | 571ms | 0 | 0，删除 1 | 18，另移除 5 |

首次建库的剩余阶段约 6.56 秒，明显高于索引阶段的 3.15 秒。worker 峰值 RSS 约 240 MiB，CPU 用户态与内核态时间合计约 7.90 秒。这是单个原生 worker 的数据，不包含整个桌面应用和 WebKit 的总峰值内存。

改变词项的单文件保存还收到一次后续文件系统通知，产生第二个无变化任务：293ms，扫描 1 个文件，重建 0 个文档、重写 0 个导出文件。因此该次保存实际发生了两个串行任务，不能只看第一个任务就宣称没有重复调度。

## 遍历形态补测

以下直接调用与桌面程序相同的原生 `index-only` 模式，排除正式导出。每种形态分别生成 10,000 个文件，先执行首次索引，再连续测量 5 次无变化索引。每次都验证扫描数为 10,000，后 5 次重建数为 0。

| 文档分布 | 首次 index-only | 无变化中位耗时 | 无变化范围 | 内部索引计时中位数 |
| --- | ---: | ---: | ---: | ---: |
| 全部平铺根目录 | 1,741ms | 314ms | 311–321ms | 304ms |
| 100 个子目录 | 1,600ms | 327ms | 325–335ms | 316ms |
| 1,000 个子目录 | 1,613ms | 347ms | 343–351ms | 336ms |
| 32 层公共路径，再分 100 个目录 | 2,902ms | 721ms | 708–742ms | 711ms |

这些是完整 `index-only` 路径的耗时，包含读取历史状态和重写运行快照。深路径测试也会扩大快照中的路径字符串，不能把全部差额归因于文件系统遍历或递归层数。当前实现使用队列遍历，32 层路径没有导致栈溢出或漏文件。

## 文件监听与根任务调度

| 实际操作 | worker 数量 | 扫描范围 | 结果 |
| --- | ---: | --- | --- |
| 跨 100 个目录修改 100 个文件 | 2 | 首个文件，然后全库 10,000 个文件 | 重建数为 1 + 99，全部更新已核对 |
| 跨目录修改 1,000 个文件，运行中再修改首个文件 | 2 | 首个文件，然后全库 10,001 个文件 | 第二次处理了运行中的再次修改，最终内容正确 |
| 每隔约 2 秒更新 1,000 个文件，共 30 批 | 21 | 首次定向，后续主要为全库 | worker 不重叠，最后一批 1,000 个版本全部正确 |

前两组任务从首个 worker 开始到最后一个 worker 结束，分别约 5.45 秒、5.63 秒；100 文件组的首个 worker 接受了调用栈采样，计时包含采样干扰。

持续写入组覆盖约一分钟的 30,000 次文件写入，从首个 worker 开始到最后一个 worker 结束约 65.57 秒。21 个任务的中位耗时为 2,941ms，累计扫描 200,021 个文件、重建 20,001 个文档。合并掉中间版本符合索引最终状态的业务目标；最后一批全部可读，没有发现最终更新丢失。

该结果同时说明当前范围合并比较粗：不同目录的待执行路径合并为公共根目录后，会重新遍历整库。根任务串行和最终一致性已验证，但高频跨目录更新仍有重复遍历成本。

## 磁盘写放大审计

在临时新增一个文档后，对 10,001 个文档执行无变化刷新，耗时 655ms；导出文件重写数仍为 0。对整个 `.ai-index` 的文件属性前后对比发现：

| 被替换文件 | 最终文件大小 |
| --- | ---: |
| `runtime-status.json` | 661 字节 |
| `runtime/index-state.json` | 144 字节 |
| `runtime/active-file-state-snapshot.json` | 1,900,047 字节 |

`runtime/export-catalog-snapshot.json` 没有替换。因此“无变化不重写导出”已验证，但“无变化不重写所有快照”并不成立。这里记录的是文件被替换及最终大小，不是内核级累计写入量；状态文件可能在一次任务内多次更新。

同一时点，文档目录快照约 8.36MB，活动文件快照约 1.90MB，搜索 manifest 约 3.45MB。定向修改一个文件仍要读取和处理整份 JSON 状态，因此扫描数为 1 不代表整次任务达到常数时间。

## 界面与缓存读视图

持续写入期间，通过记录的时间戳确认以下操作发生在原生 worker 正在运行时：

- 从根目录打开一个包含 100 个文档的目录，操作与辅助功能树采集合计 827ms，能够正常显示内容。
- 打开搜索窗口、提交查询，窗口能够响应；一次提交与辅助功能树采集合计 519ms。
- 在当前目录查询 `bulkuniqueword`，得到预期的 10 个文档。

这些是自动化操作往返时间，包含辅助功能工具开销，不能作为原生 API 延迟、帧时间或 P95 指标。

另行加载真实 Node 导出读取器，验证正式离线导出：

| 查询 | 预期数量 | 实际数量 |
| --- | ---: | ---: |
| `duringrununique` | 1 | 1 |
| `bulkuniqueword` | 999 | 999 |
| `finalversion29` | 1,000 | 1,000 |
| 已被替换的 `finalversion0` | 0 | 0 |

同一个读取器实例连续读取一个目录 20 次，缓存后中位耗时 1.12ms，范围 1.05–3.07ms。第一次离线搜索同时建立读取视图，约 116ms；后续三个不同查询分别约 12ms、9ms、3ms。查询不同，这些值不能当作同一查询的缓存加速对照。

桌面原生关键词查询使用缓存目录快照中的标题、路径和摘要过滤，并不读取离线搜索桶；因此桌面搜索和离线导出读取器分别验证，不能互相替代。

## 运行中确认的问题与优化优先级

1. **空闲页面不会自动接收监听任务的完成结果。** 后台索引和导出已完成，空闲页面的列表排序、文档和标签数量仍保持旧值；切换目录或手动刷新后恢复。代码中只有处于活动索引状态时才开启轮询，监听任务没有将开始或完成事件推送到页面。对应 `apps/web/src/features/library/useLibraryState.ts:810`。应通过原生任务完成事件更新读视图，避免额外增加永久高频轮询。本次只记录问题，没有修改业务实现。
2. **搜索桶和 JSON 序列化是当前明显的导出热点。** 改变词项的单文件更新约 2.05 秒，而词项不变约 0.81 秒。一次 1 秒调用栈采样中，519 个主线程样本有 381 个处于搜索索引构建调用链，其中包含搜索桶 JSON 序列化；该比例只代表采样窗口。对应 `apps/desktop/src-tauri/src/native_export.rs:922` 和 `apps/desktop/src-tauri/src/native_export.rs:1137`。优先评估更细的桶粒度和避免整桶重复处理。
3. **活动文件快照仍存在确定的无变化写放大。** `write_runtime_mirror_snapshots` 每轮重新读取、组装和写出整份活动文件状态。对应 `apps/desktop/src-tauri/src/native_index.rs:1055`。应保留无变化文件的版本和内容，减少全量序列化。
4. **单文件任务仍依赖全量状态读取与合并。** 实测索引阶段约 0.52–0.56 秒，即使扫描数只有 1。对应 `apps/desktop/src-tauri/src/native_index.rs:1237`。需要结合快照所有权和增量持久化继续简化，不能仅凭遍历范围缩小就宣称全部工作均已增量化。
5. **跨目录待执行任务扩大为整库。** 当前公共路径合并有利于保持实现简单，但持续写入测试中发生约 20 万次文件检查。对应 `apps/desktop/src-tauri/src/lib.rs:1491`。可以评估保留一组不重叠的目录范围，在保持根目录串行执行的前提下减少扫描。

所有 63 次原生 worker 调用均成功退出，包括 24 次遍历补测。测试核对了批量更新、运行中再次修改、最终版本、离线新增与旧词项移除、临时文档删除后的结果。此次没有修改索引业务代码，没有提交 Git 变更，也没有测试 Windows、发布构建、网络磁盘或大型二进制文档。
