# 20260616-X-File当前插件系统能力边界说明

这份文档只做一件事：把 **X-File 当前已经落地的单层插件系统到底能做什么、不能做什么、宿主和插件各自负责什么** 写清楚。

不要把它当愿景文档。这里写的内容都应该已经在仓库里存在实现，或者至少已经被测试和类型系统约束住。

## 1. 当前插件系统的核心判断

当前 X-File 的插件系统已经不是“manifest 看起来像插件”的状态，而是具备了真实运行时边界：

- 主 APP 只保留一层插件模型：`主 APP + Integration Plugin`
- assistant provider 的可见性来源于“已安装且启用插件”
- assistant runtime 已经通过插件 backend entry 动态加载
- 宿主不再写死 `codex / claude-code` runtime 初始化
- 宿主已经具备通用 `runtime.install` 框架，但不会把 provider runtime 重新收回主包

换句话说，当前的插件系统已经有**注册表、安装/更新/回滚、运行时加载、provider bridge、权限桥接、统一 DTO** 这些真实部件，不再只是 UI 假象。

## 2. 当前插件系统已经具备的能力

### 2.1 单层 Integration Plugin 模型

当前内置插件装配规则：

- `codex / claude-code` 这类集成插件可以作为程序包内置资源随包分发
- backend 启动时会自动扫描 `X_FILE_BUNDLED_PLUGIN_DIR` 指向的内置插件目录

- 内置插件不要求用户先手工执行“安装插件目录”
- provider-specific 依赖若需要热安装，仍通过 `runtime.install` 进入隔离 runtime 目录，不回收给宿主

第一版安装源收敛策略：

- 只支持本地目录源
- 不接远程插件商店
- 不接云端授权

这不是缺功能，而是故意先把状态机、回滚和边界做扎实。

### 2.6 assistant 权限桥已经插件化

当前权限请求链路已经切到：

- 插件负责构造 provider-specific 审批响应

- 结构化 `AssistantPermissionRequest.metadata`
- `file_change` 的 `primaryPath + changes[] + diffSummary`
- 插件权限 payload 联合类型，避免宿主再吃 `Record<string, unknown>`

这块已经在类型系统里被收紧，不只是运行时约定。

### 2.7 结构化权限 metadata 为什么属于插件系统能力

这不是“顺手优化前端展示”，而是插件运行时边界的一部分。

如果宿主只能收到一段 provider 文本描述，那么：

- 宿主就必须重新理解 provider-specific 文本
- 前端权限 UI 就只能靠字符串猜语义
- 一旦换一个 provider，宿主又会长出新的特判

这和单层插件系统的目标正好相反。

所以当前做法是：

- provider-specific 原始权限请求由插件解释
- 插件把结果收敛成统一 permission contract
- 宿主只持久化、桥接、SSE 推送和输出统一 DTO
- 前端只消费结构化字段，不消费 provider 私有文本协议

`file_change` 的 `primaryPath + changes[] + diffSummary`、`command` 的 `command + cwd + reason`，本质上都是在把“provider 私有语义”压回插件，把“宿主统一桥接层”稳定下来。

## 3. 宿主和插件当前职责边界

### 3.1 宿主负责什么

宿主当前负责：

- 插件发现与注册表管理
- 插件安装、更新、禁用、卸载、回滚
- `runtime.install` 通用装配
- backend entry 动态加载
- provider bridge 健康检测
- assistant session 持久化
- SSE 事件下发
- 权限请求持久化与超时默认策略
- 统一 DTO 输出

宿主明确 **不负责**：

- provider-specific runtime 初始化细节
- provider-specific 权限请求解析
- provider-specific 审批响应构造
- 把 `codex / claude-code` runtime 再次打回正式安装包

### 3.2 插件负责什么

插件当前负责：

- 声明 manifest 和能力边界
- 声明 backend entry
- 构造 runtime adapter
- 解释 provider-specific 原始请求
- 生成标准化权限请求
- 构造 provider-specific 审批响应
- 在 `system-cli` 或 `npm-runtime` 下提供自己的 provider runtime

## 4. 当前 assistant 插件化还差哪几块

当前已经有“真实 backend entry + 最小会话链路 + 权限桥”的闭环，但还没有全部做完。还差的主要是这几块：

- session lifecycle 仍主要由宿主管理
  - 会话持久化、恢复、超时、SSE 生命周期仍在主 APP
  - 这不算问题，但说明插件还没有拿到更深的 lifecycle hook
- 权限语义 contract 还只是第一版
  - `command / file_change / other` 已够当前链路使用
  - 但更复杂的 diff block、批量审批、细粒度参数展示还没统一
- `claude-code` 还没有补到和 `codex` 同等级的权限桥能力
  - 当前最完整的插件权限链路证明主要还是 `codex`
- `npm-runtime` 还是 installer skeleton
  - 已能做隔离安装和 backend entry 加载
  - 但还没有重装、日志、离线缓存、签名/hash 校验等治理能力
- 插件分发体系还没做
  - 目前只支持本地目录源
  - 还没有远程源、插件商店和云端授权

这些缺口里，真正最该优先继续切的，不是继续给宿主加 provider-specific 分支，而是继续补统一 contract 和宿主通用框架。

## 5. 当前已经验证过的真实链路

当前仓库里已经至少证明了这些链路：

1. backend entry 可以动态装载
2. assistant provider 只来自“已安装且启用插件”
3. provider bridge 能返回缺命令 / 未登录 / 健康三类诊断
4. 至少一条 assistant 会话链路可以通过插件 backend entry 跑通
5. 权限请求可以由插件发起、宿主桥接、前端回复、插件收到审批结果
6. `file_change` 权限请求可以带路径列表、操作类型和可选 diff 摘要

## 6. 当前还没有做的东西

这里专门写清楚，防止后面的人误以为已经做完：

- 还没有远程插件商店
- 还没有云端授权体系
- 还没有多层插件模型
- 还没有把 session lifecycle 下切到插件 hook
- 还没有统一 diff block contract
- 还没有 runtime 重装按钮、安装日志查看和离线缓存
- 还没有把 `claude-code` 补到和 `codex` 同等级的权限桥能力

这几个点都不该靠宿主里继续长 provider-specific 分支来补。

## 7. 后续扩展规则

后续如果继续扩插件系统，必须遵守这些硬规则：

1. 只能继续沿用单层 `Integration Plugin` 模型。
2. 不允许为了加新 provider 再造第二套 assistant 扩展系统。
3. provider-specific runtime 必须继续归插件，不准重新塞回主包。
4. 新增权限语义时，优先扩共享 contract，不准让宿主靠字符串或 provider 名称猜字段。
5. 新增 runtime 能力时，优先扩 `runtime.install` 通用框架，不准让宿主直接承担 provider-specific 安装逻辑。
6. 如果某个扩展无法用统一 contract 表达，先停下来改 contract，不要先把特殊判断写进宿主。

## 8. 当前最重要的结论

当前 X-File 插件系统已经具备“真实插件拥有 assistant runtime”的最小闭环，但还没有完成所有后续治理能力。

最关键的结论只有两句：

- **assistant 运行时已经开始归插件，不再只是 manifest 插件化。**
- **宿主当前仍保留桥接职责，但不应该再回收 provider-specific 语义和 runtime。**

后续任何继续开发，都应该把这两句当作硬边界。
